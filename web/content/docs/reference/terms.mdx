## Intended agreement model

| Scope | Bound information |
| --- | --- |
| Identity | Buyer, seller, asset, network, deployment and payment uniqueness |
| Work | Agreement commitment, pricing/delivery criteria and principal budget |
| Timing | Funding/session limits, claim review, evidence response and ruling windows |
| Arbitration | Custom preferences, pinned default, accepted quote applicability and terminal fallback |
| Fees | Separate protocol/arbitration reserves, earning/return rules and per-case/total caps |
| Version | Contract, schema, x402 binding and supported policy capabilities |

The fee-capable schema must bind this economic policy into the authorized payment. Quote identifiers/signatures, fee commitments and replay checks require a versioned encoding; the table is not a finalized list of wire field names.

## Payment identity

Canonical encoding and payment identity must bind the full agreement to its network and contract. Changes affecting allocation or authorization cannot silently reinterpret an existing payment hash. Clients must reject unsupported required capabilities before signing.

## Existing fee-free schema

The current testnet `PaymentTerms` includes:

| Fields | Meaning |
| --- | --- |
| `payer`, `seller`, `token` | Parties and payment asset |
| `agreement`, `max_amount`, `salt` | Agreement hash, base-unit budget and 32-byte uniqueness value |
| `fund_by`, `delivery_deadline` | Funding and session deadlines |
| `buyer_arbiter`, `seller_arbiter`, `default_arbiter` | Custom preferences and pinned default |
| `review_seconds`, `response_seconds` | Review and evidence durations |
| `arbiter_seconds`, `default_seconds` | Ruling durations |
| `fallback_seller_bps` | Agreed terminal seller share in basis points |

This schema has no funded protocol/arbitration reserves. Existing amounts use integer base-unit strings. Hashes are 32-byte values represented as hex; times use Unix seconds and duration fields use seconds.

## Compatibility rules

Basic auth-capture, fee-free protected escrow and the intended fee-capable version are separate capabilities. Preserve each existing payment's original terms, contract and network. A supported-version declaration and compatibility checks must accompany the public SDK release.
