## Configure the client

Create a `ProtectedEscrowClient` for the payment’s escrow contract, RPC and network passphrase. The client prepares lifecycle actions, validates authorization and reads payment and claim state.

**SDK distribution is not fully implemented yet.** An installable release will provide the client and its versioned exports. The examples below describe its TypeScript API and assume your integration supplies the `ProtectedEscrowClient` constructor, payment identifiers and wallet adapter.

```ts
import { Networks } from '@stellar/stellar-sdk';

const client = new ProtectedEscrowClient({
  contractId: protectedContractId,
  rpcUrl: 'https://soroban-testnet.stellar.org',
  networkPassphrase: Networks.TESTNET,
});

const terms = await client.terms(paymentId);
const balances = await client.state(paymentId);
const claim = await client.claimState(paymentId, claimId);
const authority = await client.arbiter(paymentId, claimId);
```

The example assumes your configured `protectedContractId`, `paymentId` and `claimId`. Confirm deployment and network values before using them.

## Prepare, sign and submit

```ts
const prepared = await client.prepare(buyerAddress, {
  type: 'accept',
  paymentId,
  claimId,
  commitment: claim.commitment,
});

const signedXdr = await signTransaction(prepared.xdr, buyerAddress);
const result = await client.submit(prepared, signedXdr);
console.log(result.tx);
```

`signTransaction` is your wallet adapter. `prepare` simulates and validates the action. `submit` checks that the wallet did not change the prepared transaction and waits for confirmed success. Authorizing a new payment requires the seller's additional signature; see [wallets and authorization](/docs/testnet/signing).

## Action and read methods

Mutations use a typed action with `prepare`:

| Action | Use |
| --- | --- |
| `authorize` | Fund terms approved by buyer and seller |
| `claim` | Reserve payment for a delivery |
| `accept` / `settle` | Finalize acceptance or eligible undisputed delivery |
| `dispute` / `submit_evidence` | Open a case or update a party’s evidence |
| `rule` / `finalize_fallback` | Apply a valid ruling or the agreed terminal split |
| `reclaim` / `void_unclaimed` | Return eligible unused funds |

Read methods are `defaultArbiter`, `terms`, `state`, `claimState` and `arbiter`. Contract deadlines and authorization remain authoritative if state changes between simulation and submission.

## Exact amounts

Token amounts are integer strings in base units. Seven-decimal USDC represents 3.00 as `"30000000"`. Do not use JavaScript floating point for token arithmetic. Hashes and payment IDs are 32-byte values represented as hex strings.

## Funding and fees

Payment terms include `fees` with protocol and arbitration reserves, fee limits and accepted quote references. Zero-fee offers set the relevant amounts to zero. Use `fundingTotal(terms)` to calculate the total authorized amount; separate reserves do not reduce the work budget. See [terms and compatibility](/docs/reference/terms).

## Confirmation and recovery

Keep the payment ID and transaction hash for each submission. A pending result must be reconciled before another claim or payout is prepared. Read the original transaction outcome and current contract state after an interruption; see [history and recovery](/docs/protected/recovery).
