## Connect your application

The SDK connects buyer and agent clients, seller APIs and arbitration integrations to protected escrow. Configure the contract, RPC endpoint and network passphrase for the payment version you support. Verify these values before asking anyone to sign.

**SDK distribution is not fully implemented yet.** The installable release will provide versioned packages and supported-network declarations. The [TypeScript client reference](/docs/testnet/sdk) describes the integration methods; package installation instructions will accompany the release.

## Validate before funding

Check the complete agreement: delivery criteria, principal budget, asset, deadlines, arbiter selection, fallback allocation and accepted fee quotes. Present the work budget, protocol reserve and arbitration reserve separately. Compute the payment identity from the canonical terms, network and contract.

A required capability must be supported by every participating integration. Reject an incompatible offer before signing; an agent requiring protected review must not accept a basic-only payment.

## Prepare, sign and submit

1. Call `prepare` with the transaction source and the exact lifecycle action.
2. Collect any additional role authorizations requested for that call.
3. Ask the transaction source's wallet to sign the prepared envelope.
4. Call `submit` with the prepared transaction and signed XDR.
5. Track confirmation and read the resulting payment or claim state.

Preparation simulates the action and validates its authorization tree. Each role signs only its permitted call; the transaction source signs the envelope and pays network fees. Submission rejects a wallet response that changes the prepared transaction body. See [signing and authorization](/docs/signing).

## Read and reconcile state

Use `terms`, `state`, `claimState` and `arbiter` to retrieve the agreement, balances, claim status and current ruling authority. Read fresh state when preparing acceptance, evidence, a ruling or a deadline action: another transaction may have advanced the payment since the last read.

Keep the payment ID and any submitted transaction hash. If confirmation is delayed, query the original transaction before building another action. The [history service](/docs/protected/recovery) supports continuity across sessions; onchain state remains authoritative for funds and finality.

## Handle archived records

Automatic restoration is **not fully implemented yet**. The client reports when a call needs archived state restored. Recovery tooling will restore the required records and then prepare the original action again, without changing its agreement or duplicating its effect.
