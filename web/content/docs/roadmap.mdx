## Protected payments

Nyquist402's payment model covers agreed budgets, independent delivery claims, buyer review, disputes, bounded rulings and return of unused funds. The testnet demo lets you explore these steps with USDC, private case material and payment history.

Protected escrow supports separate fee reserves and arbiter quotes. Every funded payment stays bound to its accepted agreement and deployment. See [terms and compatibility](/docs/reference/terms).

## Protected x402 integration — not fully implemented yet

A seller will advertise protected payment requirements in its HTTP 402 response. Buyer and agent integrations will verify the supported network, contract, agreement, fees and arbitration policy before signing. After funding, the payment context will connect API usage to delivery claims and receipts.

The protected wire schema and compatibility rules still need to be finalized. The [payment negotiation guide](/docs/integration) explains the sequence; basic auth-capture remains a separate capability.

## SDK distribution — not fully implemented yet

The TypeScript client model covers term validation, payment identity, state reads and preparation, signing and submission of lifecycle actions. An installable SDK release will package this workflow with supported-version declarations and integration examples. The [client reference](/docs/testnet/sdk) explains the methods and the [signing example](/docs/testnet/signing) explains authorization.

## Public facilitator API — not fully implemented yet

The facilitator will expose capability discovery, payment verification, authorized submission and transaction status. Integrators will receive a transaction identity and confirmation state so interrupted requests can be reconciled before retrying. Published endpoint and schema documentation will define the public API. See [facilitator and execution](/docs/services/facilitator).

## Managed service operations — not fully implemented yet

Evidence delivery and history support the payment lifecycle. Managed operation will add published retention and deletion policies, availability guarantees, access auditing and recovery procedures. Deadline execution will monitor eligible claims and submit settlement or fallback transactions while tracking their outcomes. See [evidence access](/docs/services/evidence) and [service operations](/docs/services/operators).

## Automatic storage recovery — not fully implemented yet

Storage maintenance will keep required contract and payment records active. When Soroban archives an entry, recovery tooling will restore it before retrying the original action, preserving its terms, evidence revision and transaction history. See [history and recovery](/docs/protected/recovery).

## Mainnet service — not fully implemented yet

The service is in testnet. Mainnet activation requires independent security review, verified deployment configuration and operational recovery checks. Mainnet network details and service terms will be published when that release is ready.
