## Facilitator API

**The public facilitator API is not fully implemented yet.** It will expose supported payment capabilities, verify payloads, submit authorized transactions and report their outcomes. Capability discovery will identify supported networks, contracts, policies and x402 schemas.

Verification will reject incompatible terms with a machine-readable reason before submission. A submission response will identify the transaction and distinguish pending, confirmed and failed outcomes. API URLs and request schemas will be published with the service release.

A facilitator submits authorized actions. It cannot change an agreement, replace its arbiter or choose an award.

## Transaction lifecycle

A transaction moves from preparation and signing to submission and confirmation. The payment service records the transaction identity before broadcast so a disconnect cannot erase the information needed to check its outcome.

If a response is lost, reconcile the original hash with the ledger before retrying. Repeated requests, worker retries and late confirmation must resolve to the same economic result rather than create a second claim or payout.

## Deadline execution

The contract does not wake itself when a deadline passes. An eligible caller must submit a transaction for undisputed settlement or terminal fallback. Before submitting, the executor reads current state and checks the action's deadline and eligibility.

**Managed deadline execution is not fully implemented yet.** It will monitor eligible actions, retain jobs across interruptions and reconcile pending submissions before retrying. Execution status will distinguish a waiting deadline, an eligible action, a pending transaction and a confirmed result.

A race with buyer acceptance or another executor cannot create a duplicate payout because the contract rechecks the claim's state.

## Direct actions and outages

Parties can submit their authorized lifecycle actions directly. Eligible public callers can submit settlement and fallback without facilitator approval. A relay outage does not give the service a veto over acceptance, disputes, rulings or return of unused funds.

Use the payment's original network and contract, then prepare and sign the action through the [TypeScript client](/docs/testnet/sdk). Query the original transaction hash before retrying an uncertain submission.
